# DSH-054：每端唯一 Docker 环境与入口

## 目标与决定

2026-11-04，用户要求清理历史环境，每个端只保留一个 `docker-compose.yml`、
一个 `Dockerfile` 和一个进入点；历史仅在文档记录。承接尚未提交的 052/053
目录重构，保留当前成功闭环的算法、数据、模型、接口与执行参数。

- 当前三个实现各保留 `docker/Dockerfile`、`docker/docker-compose.yml` 和
  `scripts/run.sh`；真机端未实现，不造空壳。根 `docker-compose.yml` 只聚合三端。
- `run.sh` 同时作为 Compose entrypoint 和容器内唯一功能入口，提供 `idle`、
  `shell`、`exec` 以及本端业务命令。默认仅空闲，不启动采集、训练、模型或仿真。
  公共环境准备可以 source 一个 helper，但不再提供多个可执行入口包装。
- 镜像名固定为 `sim-dual-arm/simulation:current`、`sim-dual-arm/runtime:current`、
  `sim-dual-arm/learning:current`。删除 protocol/policy/dev/probe/test 等历史构建路线，
  保留 Ruckig 编译所必需的内部 build stage，不产生额外运行环境。
- 每端 Dockerfile 独立构建依赖环境，不以其他端的项目镜像为基础。运行/仿真使用
  当前 ROS 2 Jazzy 基线；学习保持 ROS-free，依赖从当前 hash lock 安装进镜像，
  不再挂载宿主 venv。业务源码、配置、数据、模型和 SDK 仍挂载，不 COPY 业务代码。
- 宿主 `scripts/env.sh` 只管理 build/up/down/shell/exec/config。Compose 持有
  build 定义与本端 `PROJECT_ENTRYPOINT`。`shell` 进入已有容器；`exec <端> --
  <功能> ...` 调用本端 run.sh，原始命令显式使用 `exec <原始命令> ...`。
  容器内 SDK 生成、测试仍从端入口调用已有真实实现，不新增宿主 Python 业务。
- 清理过时的镜像/venv绑定脚本、专用依赖锁、入口和空目录。保留有效依赖锁、
  来源记录与长期边界测试。旧历史文档正文不批量改写，删除文件的必要链接改为
  对应阶段说明；当前说明和根 README 只介绍唯一现行方式。
- 不删除数据、模型、日志、缓存、旧工作树，不提交/推送。旧项目镜像标签仅由
  主助手在新环境验收后核对并清理，不执行全局 prune，不触及其他项目。

  `scripts/run.sh`；根 `docker-compose.yml` 只 include 三端。删除旧根
