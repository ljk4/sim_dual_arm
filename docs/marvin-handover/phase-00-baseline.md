# P00 基线与实施准备

P00 基线已交付，见[实际记录](deliveries/phase-00.md)。后续沿用未受影响结果，按当前工作树和修改范围补检查；当前下一步为 P01A，不重新启动全套基线。

## 实施任务

1. 阅读 [RULES.md](../../RULES.md)、[架构接入缺口](architecture.md)和[方案模板](../../shared/scenarios/_template/README.md)。记录当前 Git 分支/HEAD、工作区修改/删除、新任务书与源资产位置；这些记录描述实施基线，不把未提交改动当成可恢复的提交。
2. 保留现有工作树。若采用隔离工作树，先明确哪些未提交文件构成本次基线并复制到隔离环境，记录工作树、会话与日志位置。不要在旧提交上遗漏当前方案改动，也不恢复用户已删除的目录或产物。
3. 核对三个容器的实际镜像、代码挂载、ROS SDK/Policy SDK、LeRobot 固定版本、GPU/EGL 和可用数据盘。以当前脚本与 Compose 为准；本阶段不调整部署配置，必要变更在所属阶段实施。
4. 核对 `build/`、`var/` 与容器 `/build`、`/data` 的真实对应关系，再选择新产物目录。当前文档中的 `/data` 指容器数据根，不据此创建宿主机根目录 `/data`。历史实验记录中的路径/模型不作为现存产物证明。
5. 按修改范围选择 Panda 基线，在拥有依赖的端内执行：MuJoCo 场景/控制/运动学在 simulation，ROS/SDK/MCAP 在 runtime，ACT 与数据转换在 learning。全仓测试可用于发现环境缺口，但跨环境缺依赖的失败须单列，不当作该端功能结果，也不为消除失败向 learning 引入 ROS。
6. 若当前环境能运行 Panda 程序示教，保存一次完整任务的状态、控制反馈与结果作为物理回归对照。缺少已生成 SDK 或资产时，先按现行入口恢复这些依赖；无需为基线重新训练旧模型。
7. 沿本次实际调用链标出端内机制、机器人/算法适配和任务实现的现有归属，确认优先接入点：机器人装配/I/O、任务插件、Teacher 扩展。复用 [architecture.md](architecture.md) 已确认的缺口，仅补充源码核对发现的变化，P00 不提前实施跨端重构。

## 建议的产物布局

宿主机产物统一放项目的 `var/`，容器内对应 `/data`。按运行分配新目录，实际名称写入交付记录：

```text
var/
├── marvin-handover/<run-id>/          # 模型/运动诊断、快照、阶段日志
├── campaigns/marvin_handover_diag/   # 本任务独立台账、原始记录和筛选清单
├── learning/marvin_handover_diag/    # 数据、训练预算、runs 和 bundles
└── prepared/marvin-handover-<run-id>/ # simulation/runtime/policy 准备产物
```

沿用工具已有的 profile、bundle、SDK 身份校验。阶段记录写实际路径和身份即可，不额外生成源码或每条记录的摘要台账。

## 完成条件与交付

- 已明确当前可复现的代码/配置基线、容器挂载和实际可用依赖。
- Panda 相关测试与一次示教对照具备可用证据；已知失败区分实现缺陷、失效测试与环境依赖。后续阶段若依赖其验证能力，先在所属阶段修复或取得正确环境的结果。
- 新方案命名、产物根与预算归属确定，旧目录保持完整。
- P01/P02 的机器人装配与执行接入、P03/P04 的任务/Teacher 接入边界明确，learning 以验证现有 ACT 档案/配方兼容为起点；hardware 保持边界说明。
- `deliveries/phase-00.md` 记录实际命令、结果和证据路径；不以历史通过数量代替本次结果。

本阶段只建立必要对照，不做全仓整理。P00 已记录的两条运动学失效测试在 P02B 修正，MCAP 在 runtime 验证。每次交付提供完整测试文件路径、工作目录与容器入口，范围简写不能作为可复制命令。相关回归范围见 [P06](phase-06-acceptance.md)。
